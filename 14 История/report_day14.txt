ЗАДАНИЕ 3. План диалога из семи действий
1. Получить одну строку пользователя и убрать пробелы по краям.
2. Проверить команду: выход, очистить, история (сравнение без учёта регистра).
3. Проверить пустой текст: если после strip() ничего нет — пропустить ввод.
4. Добавить вопрос в messages с ролью user.
5. Собрать ChatCompletionRequest с накопленным списком messages и отправить его.
6. Вывести ответ помощника.
7. Добавить ответ в messages с ролью assistant, записать обмен в журнал.
Повторяются действия 1–7 на каждом проходе цикла. Подключение GigaChat и
SYSTEM_PROMPT создаются один раз до цикла и не пересоздаются после реплики.

ЗАДАНИЯ 4–6. История без API (history_demo.py)
Создан список: system → user → assistant. Модель не вызывалась.
После одного полного обмена длина messages = 3, роли:
  1. system
  2. user
  3. assistant
После двух обменов длина = 5, роли: system, user, assistant, user, assistant.
Предсказание до запуска: 3 и 5. Совпало.
Если добавить ещё одну пару user/assistant, длина станет 7.
Число обменов и len(messages) отличаются на 1, потому что system не входит
в обмены: len = 1 + 2 × (число полных обменов).

Почему недостаточно сохранять только вопросы пользователя?
Уточнение «Расскажи подробнее про второй вариант» невозможно понять без
предыдущего ответа помощника, где этот второй вариант был предложен.

ЗАДАНИЯ 7–9. Цикл ввода без API
Проверочная последовательность в history_demo.py: обычная фраза → пустая
строка → «история» → «очистить» → обычная фраза → «выход».
Наблюдения:
- обычная фраза: длина выросла на 2 (user + тестовый assistant);
- пустая строка и одни пробелы: длина не изменилась, ввод пропущен;
- «история»: длина не изменилась, роли только показаны;
- «очистить»: длина стала 1, остался system;
- после очистки обычная фраза: длина снова 3;
- «выход»: цикл завершён, в историю команда не попала.
Полная расшифровка вывода сохранена в history_result.txt.

Ошибка А: если создавать messages внутри while перед каждым вводом, каждый
проход начинается с пустого списка и предыдущие обмены теряются. Список нужно
создавать один раз до цикла.
Ошибка Б: если проверка «выход» стоит после добавления user и обращения к API,
команда уйдёт модели как обычный вопрос, программа сделает лишний запрос и
получит ответ. Команды надо проверять до добавления сообщения и до API.

ЗАДАНИЯ 10–12. Основной чат (main.py)
messages создаётся до цикла: первое сообщение — system с SYSTEM_PROMPT.
Цикл while находится внутри with GigaChat. На каждом проходе:
проверки → добавление user → новый request со всем списком → ответ →
добавление assistant. Старый шаблон из трёх обязательных полей заменён
на одну реплику; уточнения идут обычными сообщениями.

Реальный диалог из четырёх пользовательских сообщений (один запуск):

1) Пользователь: Мой код: def divide(a, b): return a / b; print(divide(10, 0)).
   Ошибка: ZeroDivisionError: division by zero. Как исправить?
   Помощник: Причина: деление на ноль. Объяснение: в Python деление на ноль
   недопустимо и вызывает ZeroDivisionError; в коде b = 0. Исправленный код:
   def divide(a, b): if b != 0: return a / b else: raise ValueError("Деление на ноль").
   Совет: проверяйте делитель до деления.
   [В истории сообщений: 3, обменов: 1]

2) Пользователь: А как изменить мою функцию divide, чтобы она проверяла
   делитель и не падала?
   Помощник: Исправленный код: def divide(a, b): if b == 0: return None
   else: return a / b. Совет: проверять делитель в начале функции.
   [В истории сообщений: 5, обменов: 2]
   (Ответ построен на функции из предыдущей реплики, а не на новом описании.)

3) Пользователь: Добавь в эту же функцию проверку, что делитель — целое число
   от 1 до 100.
   Помощник: def divide(a, b): if b == 0 or b < 1 or b > 100: return None
   else: return a / b. Совет: проверять входные данные заранее.
   [В истории сообщений: 7, обменов: 3]

4) Пользователь: Объясни, почему проверку типа лучше делать до деления,
   а не ловить исключение после.
   Помощник: проверка до операции предотвращает ошибку заранее, ускоряет код
   и упрощает отладку; пример: if not isinstance(b, int) or b < 1 or b > 100:
   return None, затем return a / b.
   [В истории сообщений: 7, обменов: 4]

После четвёртого обмена сработало сокращение: осталось 7 сообщений
(system + три последние пары), роли: system, user, assistant, user, assistant,
user, assistant.

ЗАДАНИЯ 16–17. Ограничение истории
max_pairs = 3. Правило: оставить system, взять последние 2 × max_pairs обычных
сообщений и объединить: [messages[0]] + messages[-2 * max_pairs:].
Сокращение выполняется только после успешного ответа assistant и только если
длина больше 1 + 2 × max_pairs = 7.
Проверка в history_demo.py на четырёх различимых парах:
- до сокращения длина 9;
- после сокращения длина 7;
- первый элемент system — True;
- первая пара удалена — True;
- сохранены пары 2, 3, 4 — True;
- порядок user/assistant не нарушен — True.
Перед следующим запросом после новой реплики в списке может быть 8 сообщений
(system + 3 пары + новый user) — это нормально; после ответа снова не больше 7.
Ограничение: если нужное условие было только в удалённой паре, помощник может
его потерять. В таком случае он должен уточнить данные по правилам SYSTEM_PROMPT.
Вывод модели не доказывает удаление: состав списка проверен отдельно в демо.

ЗАДАНИЯ 18–20. Текстовый журнал chat_history.txt
Журнал ведётся в режиме a (дозапись), русский текст в UTF-8. Перед циклом
добавляется строка «=== Новый запуск ===». После каждого успешного обмена
пишутся «Пользователь: …» и «Помощник: …», между обменами пустая строка.
При «очистить» дописывается «[История текущего диалога очищена]».
Проверка: выполнено 4 обмена, затем очистка, затем ещё 1 обмен. В messages
после очистки и нового обмена 3 элемента, а в файле остались все 5 обменов
по порядку и метка очистки. Повторный запуск программы добавил новый
«=== Новый запуск ===», прежний текст сохранился. В памяти нового запуска
только system: журнал автоматически в модель не загружается.
Счётчик успешных обменов: 5 за запуск (4 до очистки + 1 после). Очистка
контекста счётчик не сбрасывает. При выходе выведено «Успешных обменов
за запуск: 5».

ЗАДАНИЕ 22. Изменение программы
Лимит изменён с трёх пар на две (max_pairs = 2). Новый предел после полного
обмена: 1 + 2 × 2 = 5 сообщений. Проверка на четырёх парах:
- длина после сокращения 5;
- роли: system, user, assistant, user, assistant;

САМОПРОВЕРКА
- Роли system, user, assistant различаю: system — правила, user — реплика
  пользователя, assistant — ответ модели.
- break завершает цикл, continue пропускает остаток текущего прохода.
- messages создаётся до while, иначе история теряется.
- Сохраняются полные пары user/assistant; system всегда первый.
- Контекст (messages) и журнал (chat_history.txt) — разные хранилища:
  журнал не передаётся модели автоматически.
- Могу изменить max_pairs и рассчитать новый размер истории.
- История работает за счёт передачи накопленного списка в каждый запрос,
  а не только за счёт текста в prompts.py.
